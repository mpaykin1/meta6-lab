# РАБОЧИЙ ЧАТ МГ/МГЛ — исполняемый цикл

**Команда владельца:** «Работай по МГ и МГЛ: открой https://github.com/mpaykin1/meta6-lab/blob/main/automation/prompts/CHAT_RABOTA.md и выполняй его целиком, по кругу, без вопросов ко мне».

## 0. Восстановление — всегда первым

1. Работай с `mpaykin1/meta6-lab`. `mpaykin1/meta6` — **только чтение**. Не менять и не сливать исходный `meta6`.
2. Читай актуальные `AGENTS.md` обоих репозиториев, `CLAUDE.md` (если существует), `ZADACHI.md`, `DISPETCHER.md`, `SMENA.md`, `rules/09-platforma/FINISH.md`, `rules/09-platforma/ZANYATO.md`, `rules/06-rabota-ii-s-kodom/TABLITSA_ZADACH.md`, `rules/06-rabota-ii-s-kodom/KONTUR_BEZ_OSHIBOK.md`, `OSHIBKI.md`, `automation/prompts/MG_PYAT_AVTOZADACH.md`.
3. Сравни фактические PR, SHA ветки, CI и статус с записью смены. Предыдущий текст чата и прошлые статусы не считай доказательством. Готовое с подтверждённым SHA/PR не повторяй.
4. Рабочая задача уже есть в `ZADACHI.md` — продолжи её. Новую задачу **до начала** добавь первой строкой под шапкой таблицы и запушь в `main` **только эту строку**. Не создавай дубли. Для пункта FINISH перед изменением проверь `ZANYATO.md`.
5. Если `DISPETCHER.md` в `main` отсутствует, **не выдумывай карточки и не заявляй о запущенном диспетчере**. Проверь [PR #227](https://github.com/mpaykin1/meta6-lab/pull/227), его CI и право на слияние. Используй `ZADACHI.md` и PR лишь для ремонта зависимого диспетчера, пока не появился реальный `DISPETCHER.md`.

## 1. Захват работы из диспетчера

1. Читай `DISPETCHER.md` из `main`, не из памяти. Приоритет очереди: **конфликты → красные проверки → 🛑 ЗАВИС → 💤 ЗАБРОШЕНО более 2 суток**; внутри группы — открытые пункты `FINISH.md`.
2. Пропускай закрытые/слитые PR, строку `НУЖЕН CLAUDE`, свежие захваты других исполнителей и изменения на чужой активной ветке. В блоке `НУЖЕН CLAUDE` ничего не сливай.
3. Выбери верхнюю доступную карточку, проверь её PR, ветку и актуальный SHA. Поле `Взял` — аренда на **2 часа**, а не вечная блокировка; актуальный новый коммит исполнителя имеет приоритет над таймером. Перед захватом повторно проверь, что карточку никто не взял.
4. В `SMENA.md` закрепи **идентификатор этого чата/исполнителя**, PR, SHA, время UTC и действие. Зафиксируй захват на GitHub до начала работы. Если другая сессия опередила — не переписывай её захват: возьми следующую карточку.
5. Не изменяй одновременно один файл из нескольких веток. Не форсируй чужие коммиты. У тебя только задачи МГЛ; для МГ допустимы чтение, диагностика, отдельный PR **в МГЛ**, но не запись в МГ.

## 2. Цикл одной карточки

1. **DISCOVER:** прочитай описание PR, изменённые файлы, проверки именно на последнем SHA, комментарии Claude, текущий `main` и связанные записи `OSHIBKI.md`. Отделяй реальные ошибки от очереди, отменённых запусков и недоступных логов.
2. **IMPLEMENT:** устрани корневую причину в существующем рабочем коде; не подгоняй проверки под результат. Не меняй незапрошенное. Для дефекта кода добавь запись `OSHIBKI.md` и ловушку по К3; новой проверке нужны минимум три мутации, одна обманная.
3. **PR:** коммить в существующую ветку карточки или в новую `lab/*` для отдельного, не пересекающегося изменения. PR должен быть узким, с описанием сделанного и ещё не сделанного. Пуш и запись «сделано / дальше» после каждого шага; длительная сессия — не реже раза в 10 минут.
4. **CI:** проверь все обязательные проверки по текущему SHA (включая KONTUR Guard, META GAMES guard, бота по затронутой игре и независимые проверки). `queued`, `in_progress`, `cancelled`, `unknown` — не зелёные. При выполнении CI можно заняться следующей независимой карточкой, но не заявлять о слиянии.
5. **FIX:** после красного прогона прочитай точный job log и исправь код. **Максимум две реальные неуспешные попытки исправления** одной причины; если обе подтверждены логами — запиши `НУЖЕН CLAUDE: <причина> <ссылка>` в PR и `SMENA.md`, переходи дальше. Очередь CI попыткой исправления не является.
6. **MERGE:** только `meta6-lab`, только после актуального зелёного CI, прохождения бота и перекрёстной проверки на свежей базе. Отказ от самостоятельного слияния, если затронуты `.github/workflows/`, охранники, `FINISH.md`, `KONTUR_BEZ_OSHIBOK.md`, ядро бота, принятые оригиналы или ослаблены проверки. Такие PR — `НУЖЕН CLAUDE`.
7. **MEASURE:** после разрешённого слияния проверь реальный `main` и игровой результат, если затронута игра. Красный `main` после слияния → исправление или разрешённый revert, не объявлять успех.
8. **NEXT:** запиши итог со ссылкой на commit/PR/Actions в `SMENA.md`; перейди к следующей доступной карточке. Каждый запуск обрабатывает **до трёх верхних карточек**, не повторяя готовые.

## 3. Защита от зависания и правила результата

- После каждого шага сохраняй точный SHA, номер PR, текущую проблему и **следующий конкретный шаг** в `SMENA.md`. Это точка восстановления, не отчёт владельцу.
- Не создавать отдельные отчёты, handoff, evidence или неподтверждённые статусные файлы. Технические подтверждения — ссылки на GitHub.
- Не менять `scripts/zadachi/`, `.github/workflows/zadachi-watch.yml`, `scripts/meta-bot/` (ядро), `FINISH.md`, `KONTUR_BEZ_OSHIBOK.md`, принятые оригиналы, требования FPS, таймауты, метрики. Не включать рекламу, Earn, аккаунты, Steam и Google Play до разрешённого финиша.
- После восстановления очереди проверить **через два часа** (в отдельном разрешённом запуске), уменьшилось ли число зависших задач. Не обещать самостоятельную фоновую работу без настроенной автозадачи.
- Если доступная задача есть, итогом цикла должен быть **реальный коммит с улучшением**, а не один анализ или список блокеров. Если изменение невозможно безопасно, записать причину и переключиться на другую карточку.
- В ответе владельцу — кратко: ссылка на PR или SHA, только то, что **осталось**. Не выдавать PR за работающую опубликованную игру.

## 4. Повтор

Повторяй: **восстановление → захват → исправление → PR → CI → допустимое слияние → измерение → следующая карточка**. Между сессиями продолжение возможно по данным GitHub; непрерывное выполнение вне текущего запуска требует действующей автозадачи.

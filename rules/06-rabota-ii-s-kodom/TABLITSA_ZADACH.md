Пароль: `zadachi`. Таблица: [ZADACHI.md](https://github.com/mpaykin1/meta6-lab/blob/main/ZADACHI.md) в корне `mpaykin1/meta6-lab` (одна на МГ и МГЛ).

Зачем: владелец и Claude с одного взгляда видят, какие задачи завершены, а на каких ChatGPT завис и его надо толкнуть.

1. **Взял задачу — сразу строка.** ChatGPT (любой чат и любая автозадача), взяв ЛЮБУЮ задачу по МГ или МГЛ, первым действием добавляет строку первой под шапкой таблицы и пушит в main meta6-lab только эту правку: `| взято | <задача простыми словами> | МГ или МГЛ | <кто: «чат ChatGPT» или имя автозадачи> | <ветка или —> | — | <время UTC, ГГГГ-ММ-ДД ЧЧ:ММ> | — |`. Без строки работу не начинать.
2. **Статус ставит сторож, а не агент.** `ZADACHI watch` (GitHub Actions, каждые 30 минут, без ИИ) берёт правду из GitHub: PR слит → ✅ ГОТОВО; закрыт без слияния → ✖; последний коммит меньше часа назад → 🔨 В РАБОТЕ; больше часа → ⚠ молчит; больше 3 часов → 🛑 ЗАВИС — ТОЛКНУТЬ; больше 2 суток → 💤 ЗАБРОШЕНО. Слово «готово», написанное агентом при неслитом PR, сторож стирает.
3. **Задача без ветки** (настройка автозадач, проверка, ответ): закончил — сам замени статус на `ГОТОВО: <ссылка-доказательство>` (коммит, прогон Actions, issue). Без ссылки сторож считает задачу зависшей.
4. **Не можешь закончить** — статус `НУЖЕН CLAUDE: <причина одной фразой>`; сторож его сохраняет.
5. **Строки не удалять и чужие не править.** Не записал задачу — сторож сам добавит её из открытых PR с пометкой «сам не записал»; это считается нарушением правила.
6. **Зависшее продолжают, а не начинают заново:** строка «ЗАВИС» с веткой — следующий запуск продолжает с последнего коммита этой ветки.
**6а. Не плодить записи одного PR (обязательно для всех автозадач и чатов).** Перед записью нового задания перечитать свежий `ZADACHI.md` из `main`. Искать совпадение сначала по паре `репозиторий + номер PR`, а если PR ещё не открыт — по паре `репозиторий + имя ветки` (точное совпадение). Если строка уже есть, **продолжить её**, а не добавлять новую; старые строки истории не удалять. При взятии старой задачи допускается обновить её исполнителя, время захвата и ссылку на фактический результат, **не меняя столбец статуса сторожа**. После открытия PR вписать его номер в существующую запись. Перед сохранением повторно проверить актуальный blob SHA таблицы: при конфликте обновления повторить чтение и поиск, не создавать дубль слепым повтором push. В итоговых очередях группировать дубли по `repo+PR` / `repo+branch`, не считать строки отдельными задачами.

**6б. Сначала ремонт своей ветки.** Строку ⚔ КОНФЛИКТ или ❌ КРАСНЫЕ со своей веткой чинить до новых задач: конфликт — обычный merge актуального main с сохранением обеих сторон и push без force; красные — открыть лог упавшего job, исправить причину и push. На новом HEAD заново проверить обязательный CI. Защищённые пути принимает Claude; прежнее разовое разрешение другому чату не даёт новым агентам права менять сторож.

7. Не менять `scripts/zadachi/` и `.github/workflows/zadachi-watch.yml` (файлы Claude). ZANYATO.md остаётся замком для пунктов FINISH; строки из него сторож переносит в таблицу сам.
8. **Claude:** в каждом отчёте владельцу о МГ/МГЛ и при ежедневной проверке сначала смотрит ZADACHI.md и называет, кого толкнуть.

## ДОВОДЧИК: ОБЯЗАТЕЛЬНОЕ ЗАВЕРШЕНИЕ РАБОТОЙ (решение владельца, 10.11.2026)

9. **Каждый отчёт доводчика заканчивается реальным улучшением.** Сначала выполнить хотя бы одно безопасное изменение в коде, содержимом или правилах, запушить и приложить ссылку на SHA. Одного анализа, списка блокеров, переписывания журнала или эскалации Claude недостаточно. Если безопасного изменения нет — не заявлять о завершении; оставить точную незавершённую задачу.
10. **Продолжать с фактического GitHub HEAD, а не со старого отчёта.** Перед каждым изменением PR повторно прочитать head SHA, base SHA, diff, состояние проверок и `DOVODKA.md`. Если другой агент обновил head, не применять старые выводы и не делать force push. Пересчитать diff и CI на новом SHA.
11. **CI оценивается строго на текущем head.** Успех проверок старого коммита не разрешает слияние нового. `queued`, `in_progress`, отсутствие проверок, `cancelled` или `unknown` не являются ни зелёным, ни доказательством дефекта. При очереди оставить `🔁 НЕ ДОДЕЛАНО`, ссылку на run и текущий SHA; не ставить `НУЖЕН CLAUDE` только из-за ожидания.
12. **Claude — исключение, не замена исправления.** После двух реальных попыток исправления с доказательствами и красными прогонами можно поставить `НУЖЕН CLAUDE`. Если код ещё не менялся, это не две попытки. Пересечение PR — повод сверить конкретные файлы, перенести уникальный работающий код, а не автоматически объявлять дубль.
13. **Не путать промежуточное слияние с готовностью.** Merge `main` в ветку, правка `DOVODKA.md` и зелёный отдельный job — промежуточные шаги. `ГОТОВО` для PR означает только GitHub `merged=true` с SHA merge/squash; для задачи без PR — проверенное изменение с прямой ссылкой на коммит.
14. **Журнал восстанавливается и остаётся точным.** В `DOVODKA.md` фиксировать `СЕЙЧАС ДЕЛАЮ` до изменения, затем SHA, фактическое состояние и следующий шаг. Не удалять из `ОСТАЛОСЬ` пункт со статусом `🔁 НЕ ДОДЕЛАНО`; закрытые пункты переносить в журнал, сохраняя историю. Состояние `НУЖЕН CLAUDE` перепроверять при появлении нового коммита.
15. **Границы доступа.** `meta6` только чтение и без слияний; `meta6-lab` — через ветки и PR, кроме разрешённых владельцем отдельных коммитов журнала и таблицы в `main`. Не ослаблять проверки, ловушки, защищённые workflow и скрипты сторожа. Файлы `FINISH.md` и их статусы изменяет только Claude по правилам финиша.

## ДОВОДЧИК PR — ПРОВЕРКА ФАКТОВ И РЕАЛЬНОЕ УЛУЧШЕНИЕ (10.11.2026)

16. **Не подменять состояние GitHub.** `mergeable=false` само по себе не доказывает конфликт: прочитать `mergeable_state` и актуальные base/head. `mergeable=null` / `unknown` — состояние ещё вычисляется, запрос повторить. `action_required` не равен `failure`: сначала выяснить, нужно ли разрешить GitHub Actions. `queued` — ни зелёный, ни красный.
17. **Снимок очереди обновлять по источнику.** Перед записью `docs/progress/JOBS_TABLE.md` получить открытые PR обоих репозиториев, исключить закрытые и слитые, сохранить UTC. При изменении HEAD повторно читать CI. `JOBS_TABLE.md` — снимок; `ZADACHI.md` — основная таблица задач.
18. **Измерения по типу изменения.** Для игрового рендеринга сравнивать мобильные p95 и draw calls ветки и main на одинаковом устройстве, сцене и настройках. Без реальных измерений не писать `0`, `pass` или выдуманный FPS. Для PR без изменения игровых файлов — `не применимо: игровой рендер не менялся`; обязательные CI и проверки целостности остаются.
19. **Merge только при доказанной готовности.** Непосредственно перед merge проверить draft, текущий HEAD, mergeability, все обязательные проверки на этом SHA и реальные метрики, если применимы. Один зелёный job не заменяет остальные. В `meta6` слияние запрещено.
20. **Каждый запуск заканчивать полезной правкой.** После диагностики исправить минимум один подтверждённый дефект кода, конфликта, алгоритма или действующего правила, запушить SHA и отметить в `MERGE_PROGRESS.md` и общей таблице. Только изменение статуса не является улучшением. Если безопасной правки нет — не объявлять задачу завершённой.
